## 1. Customer Flow

### 1.1 A New Customer Is Created

#### Frontend (Desktop UI)

| Step | File | Lines | What Happens |
|------|------|-------|--------------|
| 1 | `apps/desktop/ui/src/components/CustomersSection.tsx` | 760–783 | User fills form (name, phone, address). Duplicate name detection runs on 450ms debounce (`isNameDuplicate`). If name match found, phone becomes required. |
| 2 | `CustomersSection.tsx` | 326–420 | `handleCreateCustomer()` validates required fields, builds a `MeasurementProfile` object with a random UUID for the selected garment type, then POSTs to `/api/customers`. |
| 3 | `App.tsx` | 27–52 | Global `fetch` override automatically attaches `Authorization: Bearer {token}` header to all `/api/` requests from Supabase session. |

#### Backend (Express Server)

| Step | File | Lines | What Happens |
|------|------|-------|--------------|
| 4 | `packages/server/src/index.ts` | 929–1028 | `POST /api/customers` — Validates `name` is non-empty. Performs duplicate name check (`.ilike("name", ...)`). Performs phone-based deduplication — if phone exists, returns `{ alreadyExists: true, customer }`. |
| 5 | `index.ts` | 935 | Clean phone: if empty, generates `NO-PHONE-{random}` as a placeholder so DB uniqueness constraints don't collide. |
| 6 | `index.ts` | 992–1007 | Inserts customer into Supabase `customers` table or SQLite via `db.createCustomer()`. |
| 7 | `index.ts` | 1011–1021 | **Simultaneously** inserts a `measurements` row with `{ data: measurements || {} }`. This is the "initial measurements" blob — always a raw JSON object, **not** the profile-based structure the frontend sends. |
| 8 | `index.ts` | 1023 | Calls `logAction("CREATE_CUSTOMER", ...)`. |

#### Local DB Path (Electron)

| Step | File | Lines | What Happens |
|------|------|-------|--------------|
| 6b | `packages/server/src/db.ts` | 265–281 | `createCustomer()` — generates UUID `v4`, executes INSERT with all fields, returns the row. |
| 7b | `db.ts` | 324–343 | `upsertMeasurement()` — checks for existing measurement row for this customer; if none, inserts; if exists, updates. Always overwrites the entire `data` field. Calls `JSON.stringify(measurementData)`. |
| 8b | `index.ts` | 961 | `sync.syncAfterMutation("customers", ...)` — queues the mutation for background sync to Supabase. |

#### Database Tables Affected

| Table | Operation | Key Columns |
|-------|-----------|-------------|
| `customers` | INSERT | `id` (UUID gen_random_uuid), `name`, `phone`, `address`, `email`, `notes`, `shop_id`, `created_by`, `updated_by`, `created_at`, `updated_at` |
| `measurements` | INSERT or UPSERT | `id` (UUID), `customer_id` (FK → customers.id), `data` (JSONB), `created_by` |
| `audit_logs` | INSERT | `action = 'CREATE_CUSTOMER'`, `record_id = customer.id` |

#### Customer ID Generation

- **SQLite (local):** UUID v4 via the `uuid` npm package (`db.ts:270`).
- **Supabase (cloud):** `gen_random_uuid()` PostgreSQL function in the schema (`schema.sql:128`).
- **No sequential/readable IDs** are generated for customers — only UUIDs.

#### Duplicate Customer Prevention

**Two-layer strategy:**

1. **Name-based (frontend + backend):** If a customer with the same name exists, the phone field becomes required. This is a soft check — duplicates with different phone numbers are allowed.
2. **Phone-based (backend only):** If an exact phone match exists, the API returns `{ alreadyExists: true, customer }` (HTTP 200). The frontend shows an alert and auto-selects the existing customer.

**Critical gap:** A customer can be created with `phone = "NO-PHONE-{random}"` when no phone is provided. This means if `Customer A` is created without a phone, then `Customer B` is created later also without a phone, they will NOT trigger the phone dedup check (different autogenerated phone values). Only the name soft check applies.

### 1.4 A Customer Is Deleted

| Step | File | Lines | What Happens |
|------|------|-------|--------------|
| 1 | `CustomersSection.tsx` | 568–588 | `handleDeleteCustomer()` → `confirm()` dialog → `DELETE /api/customers/{id}`. |
| 2 | `packages/server/src/index.ts` | 1077–1116 | `DELETE /api/customers/:id` — verifies ownership, **cascading delete**: first deletes all `measurements` rows for this customer, then deletes the customer row. |
| 3 | `index.ts` | 1111 | Logs `DELETE_CUSTOMER`. Calls `sync.syncAfterMutation("customers", ...)`. |

**IMPORTANT:** Orders are NOT deleted when a customer is deleted. The `customers.id` FK in `orders` has no `ON DELETE CASCADE` on Supabase. However, the local SQLite schema also lacks cascade on orders. This means **orphaned orders** with a meaningless `customer_id` can exist after customer deletion.

#### Relationships Affected by Customer Deletion

| Table | Cascade? | Risk |
|-------|----------|------|
| `measurements` | Yes (explicit `DELETE` in handler + FK CASCADE on Supabase) | Clean |
| `orders` | **No** — orders.customer_id remains pointing to deleted customer | **Orphaned orders** |
| `audit_logs` | No (stored separately) | Safe |
| `sync_queue` | No (transient queue) | Safe |

## 2. Measurement Flow

### 2.1 Data Structure

Measurements use a **profile-based** model with **JSONB** storage:

```typescript
// Stored in measurements.data JSONB column
{
  "profiles": [
    {
      "id": "uuid-string",
      "garment_type_id": "gt-uuid",
      "garment_name": "Shalwar Kameez",
      "values": { "Neck": 15.5, "Chest": 42, "Length": 45 },
      "styling_preferences": {
        "collar_style": "Mandarin Collar",
        "pocket_style": "Side Pockets"
      },
      "created_at": "2026-07-22T...",
      "updated_at": "2026-07-22T..."
    }
  ]
}
```

### 2.2 A Measurement Is Created (via Customer Creation)

See [Customer Creation Flow](#11-a-new-customer-is-created). The measurements are created atomically with the customer in the same API call.

### 2.3 Measurements Are Edited

| Step | File | Lines | What Happens |
|------|------|-------|--------------|
| 1 | `CustomersSection.tsx` | 481–495 | `handleEditProfileSave(profileId)` — maps over profiles array, replaces the edited profile's values, calls `handleSaveProfiles()`. |
| 2 | `CustomersSection.tsx` | 423–454 | `handleSaveProfiles()` — PUTs complete `profiles` array to `/api/customers/{id}/measurements` with `{ data: { profiles: updatedProfiles } }`. |
| 3 | `packages/server/src/index.ts` | 1166–1241 | `PUT /api/customers/:id/measurements` — **Owner-only** (`requireRole(["Owner"])`). Upserts the entire measurement row. If row exists, updates `data` field; if not, inserts new. |

**Key observation:** The frontend always sends the **entire profiles array** on every save. There is no granular per-profile insert/update/delete. This means adding one profile = overwrite all profiles.

### 2.4 Measurements Are Reused for Another Order

| Step | File | Lines | What Happens |
|------|------|-------|--------------|
| 1 | `OrdersSection.tsx` | 498–565 | When creating an order, `useEffect` loads customer's measurement profiles via GET `/api/customers/{id}/measurements`. |
| 2 | `OrdersSection.tsx` | 503–525 | For the first booking item, creates a deep copy of the profile's measurement values into `measurement_snapshot` and `styling_snapshot`. |
| 3 | `OrdersSection.tsx` | 840–882 | On order finalization, merges each booking item's measurements back into the customer's profiles via PUT `/api/customers/{id}/measurements`. |

**The snapshot:** When an order is created, measurements are **snapshotted** into `orders.measurement_snapshot` (JSONB) and also into each `OrderItem.measurement_snapshot`. This ensures historical fidelity — editing measurements later does not change past orders.

### 2.5 Different Garment Measurements Are Handled

Each `GarmentType` has its own `measurement_fields: MeasurementField[]` array (defined in `garment_types` table or `shop_settings` fallback). Each `MeasurementProfile` is tied to a specific `garment_type_id` with its own set of measurement values.

When a user changes the garment type in the booking form, the measurement fields reset to match the new type's fields.

### 2.6 Measurement Templates / Configurations Are Loaded

**Two storage backends exist:**

1. **Dedicated table (`garment_types`):**
   - `packages/server/src/db.ts:632–638` — `getGarmentTypes()` queries the table for the user.
   - Each row has `measurement_fields` (JSON array of `{ name, required, display_order }`).

2. **Fallback to `shop_settings`:**
   - `packages/server/src/index.ts:2169–2181` — `getGarmentTypesFromSettings()` reads from `shop_settings` with key `{userId}:garment_types`.
   - This is used when the Supabase project does not have the `garment_types` table.

### 2.7 Measurement History

**There is NO measurement history/versioning.** Every save (`upsertMeasurement`) completely overwrites the `data` field. The `updated_at` timestamp tracks the last update, but no audit trail of previous measurement values is stored for measurements specifically.

Audit logs record `"UPDATE_MEASUREMENTS"` / `"CREATE_MEASUREMENTS"` actions but do **not** include `previous_value` or `new_value` for measurement data — the audit entry includes only `{ customer_id }` with no diffs.

### 2.8 Database Tables for Measurements

| Table | Purpose | Key Columns |
|-------|---------|-------------|
| `measurements` | Stores measurement profile data | `id` (PK UUID), `customer_id` (FK → customers), `data` (JSONB profiles array), `created_by` |
| `garment_types` | Defines available garments and their measurement fields | `id` (PK UUID), `name`, `measurement_fields` (JSONB), `enabled`, `display_order`, `price` |
| `orders.measurement_snapshot` | Per-order snapshot of measurements (duplicated data) | JSONB in `orders` table |
| `orders.items[].measurement_snapshot` | Per-item snapshot | JSONB within the `items` JSONB array |

```

### 3.2 Backend Processing on Save

In `packages/server/src/index.ts:1477–1625`:

| Step | Operation | What Happens |
|------|-----------|-------------|
| 1 | Validation | Checks `customer_id`, `items` (non-empty array). |
| 2 | Ownership check | Verifies customer belongs to the authenticated user. |
| 3 | Snapshot measurements | Fetches current measurements from DB, stores them in `measurement_snapshot`. |
| 4 | Pipeline status | Reads shop settings to find the first enabled pipeline stage (fallback: `"Pending"`). |
| 5 | Order number generation | `ORD-{1000 + nextNum}` where `nextNum` is max existing number + 1. Falls back to `ORD-{timestamp}-{random}` if counting fails. |
| 6 | INSERT into `orders` | Creates full order record with all fields. |
| 7 | Audit log | `logAction("CREATE_ORDER", ...)`. |
| 8 | Sync (local mode) | `sync.syncAfterMutation("orders", ...)`. |
| 9 | Response | Returns order with joined `customer_name`, `customer_phone`, `customer_address`. |

### 3.3 Database Tables Affected (in order)

| Table | Operation | Notes |
|-------|-----------|-------|
| `measurements` | **UPDATE** (profiles merge back) | Not guaranteed — only if frontend chooses to save |
| `orders` | **INSERT** | Main operation |
| `audit_logs` | **INSERT** | Always logged |

### 3.4 Key: Measurement Snapshot at Creation

The backend snapshots the customer's **current measurements** into `orders.measurement_snapshot` at the time of order creation (`index.ts:1542`). The frontend also embeds per-item snapshots into each `OrderItem.measurement_snapshot` within the `items` JSONB array.

This means measurement data is **duplicated** in three places:
1. `measurements.data` (authoritative, editable)
2. `orders.measurement_snapshot` (historical, read-only after creation)
3. `items[].measurement_snapshot` (historical, read-only after creation)

### 4.1 Entity Relationship Diagram

```
auth.users
    │
    ├─── shops (created_by ── FK)
    │
    └─── profiles (id ── PK/FK → auth.users.id)
              │
              └─── shop_id ── FK → shops.id
                    
profiles (created_by) ── FK → auth.users.id
    │
    ├─── customers (created_by ── FK → auth.users.id)
    │         │
    │         ├─── shop_id ── FK → shops.id
    │         │
    │         ├─── measurements (customer_id ── FK → customers.id, ON DELETE CASCADE)
    │         │         └─── shop_id ── FK → shops.id
    │         │
    │         ├─── orders (customer_id ── FK → customers.id, ON DELETE CASCADE)
    │         │         └─── shop_id ── FK → shops.id

### 4.3 Inconsistencies

- **Supabase schema** (`schema.sql`): `orders.customer_id` has `ON DELETE CASCADE` to `customers.id`.
- **Local SQLite schema** (`db.ts:62–82`): `orders.customer_id` has `REFERENCES customers(id)` but **no ON DELETE CASCADE**. The handler in `db.ts:301–307` doesn't delete orders either — only measurements.
- **garment_types → orders**: No FK relationship exists. Orders reference garment types by **string name** in `items[].type`, not by FK. This means renaming or deleting a garment type can create data integrity issues.

### 4.4 Ownership Model

All tables use `created_by UUID REFERENCES auth.users(id)` for row-level ownership. RLS policies on Supabase enforce `created_by = auth.uid()` for all CRUD operations. In the local SQLite, ownership is enforced in application code via `WHERE created_by = ?` conditions.

### 5.2 Where Database Operations Happen

**Two parallel paths:**

```
Cloud Mode (Supabase):
  Frontend (fetch) → Express API (index.ts: dynamic Supabase queries)
                    → @supabase/supabase-js
                    → Supabase REST API
                    → PostgreSQL (Supabase managed)

Local Mode (SQLite — Electron):
  Frontend (fetch) → Express API (index.ts: calls db.* functions)
                    → better-sqlite3 (synchronous)
                    → Local SQLite file on disk
                    → sync.ts (background sync to Supabase)
```

The decision between paths is made in `packages/server/src/index.ts:20–22`:
```typescript
function useLocalDb(): boolean {
  return process.env.ELECTRON_RUN === "true" && localDbAvailable;
}
```

## 6. Problems & Improvements

### 6.1 Duplicate Logic

| Problem | Files | Description |
|---------|-------|-------------|
| **Duplicate customer name check** | `index.ts:942` (local) vs `index.ts:968` (cloud) | Same logic written twice for local vs cloud DB paths. |

### 6.2 Redundant Database Calls

| Problem | File | Lines | Description |
|---------|------|-------|-------------|
| **Get customer twice during order creation** | `index.ts:1487, 1512` | First to verify ownership, then again to get name. A single query could return all needed data. |
| **Get customer during order listing (N+1)** | `index.ts:1337–1344` | Local mode: for every order in the list, fetches the customer separately. N+1 query problem. Supabase mode uses a proper SQL join (`customers()`). |
| **Get customer during order status update** | `index.ts:1666, 1704–1708` | Also fetches customer name/phone/address on every status change just for response enrichment. |
| **Get measurements and then join customer** | `index.ts:1125–1128` | Gets customer first to verify ownership, then gets measurements. Could be a single query. |
| **Settings loading on every order list** | `index.ts:1321–1329, 1351–1359` | Every GET `/api/orders` loads full settings just to get `auto_archive_days`. |
| **Garment type usage check** | `index.ts:2183–2205` | `isGarmentTypeUsed()` loads ALL orders' items and iterates in JS — very expensive as order count grows. Should be a DB query. |

### 6.3 Missing Validation

| Gap | Location | Risk |
|-----|----------|------|
| **Phone format validation** | No server-side validation | Any format accepted |
| **Email format validation** | Only on frontend (`validation.ts`) | Malformed email can be stored |
| **Price validation (non-negative)** | No server-side check | Negative prices can be created |
| **Quantity validation** | No server-side check | Zero or negative quantities can be stored |
| **Discount consistency** | `index.ts:1593–1594` | No check that `discount_value` ≤ 100 for percentage, or that `discount_amount ≤ total_amount` |
| **paid_amount ≤ final_total** | Only on frontend (`OrdersSection.tsx`) | Backend accepts any value |
| **Order status transitions** | No validation | Order can jump from "Pending" to "Delivered" without going through intermediate stages. No FSM enforcement. |
| **Due date format** | No validation | Any string accepted |
| **Required measurement fields** | Frontend only (`CustomersSection.tsx:340–347`) | Backend accepts any measurement data |

### 6.4 Poor Data Flow

| Issue | Detail |
|-------|--------|
| **Measurement profiles always saved as whole array** | Adding one profile = PUT entire array. No partial updates. Risk of concurrent update overwrites (last write wins). |
| **Two measurement snapshot strategies** | Frontend embeds `measurement_snapshot` in each `OrderItem`. Backend also snapshots at `orders.measurement_snapshot`. These can diverge if one path fails. |
| **Customer creation = 2 DB writes (customer + measurements)** | Not wrapped in a transaction in cloud mode. If measurements insert fails, customer is orphaned. |
| **Audit log fallback** | If schema has new columns, retries without them. Silent failure — no notification to user or admin. |
| **Local mode falls back silently** | `better-sqlite3` require failure silently sets `db = undefined`. Many operations will crash at runtime. |
| **Order number generation in cloud mode** | Uses `supabaseAdmin` (service role!) to find max order number — bypasses RLS. Also reads ALL orders globally, not scoped to user. |

### 6.5 Risk of Inconsistent Data

| Scenario | Risk |
|----------|------|
| **Sync conflicts: local wins** | If two users edit the same customer offline, the last one to sync wins and the other's changes are silently lost. |
| **Sync queue failure** | `sync.ts:99–144` — items with >10 retries remain in `failed` status. No alert mechanism. No manual retry UI in the app. |
| **Customer deletion with orders** | In local SQLite, orders are NOT cascade-deleted. Customer deletion succeeds but orders become orphaned. |
| **Garment type renamed/deleted** | Orders reference garment types by string name in `items[].type`. Renaming breaks historical references. |
| **Settings cache** | `index.ts:402–458` — `settingsCache` is never invalidated for other users, only for the saving user. If an Owner updates settings, Workers may see stale cache until TTL. |
| **Legacy measurement migration** | `CustomersSection.tsx:258–269` — silently migrates old flat measurement objects to profile format. This data transformation only happens on the frontend — backend still stores the new format. |

### 6.6 Opportunities to Simplify

| Opportunity | Benefit |
|-------------|---------|
| **Extract a single `getCustomerWithOrders()` function** | Eliminates N+1 queries. Replace repeated `db.getCustomerById()` calls. |
| **Use DB-level transaction for customer+measurement creation** | Atomicity guarantee. No orphaned rows. |
| **Auto-calculate `final_total` server-side** | Removes the need for frontend to compute and trust the value. |
| **Add a `validateOrderStatusTransition(old, new)`  FSM** | Prevents invalid pipeline jumps. |
| **Use a dedicated `order_items` table** instead of JSONB `items` column | Enables FK to `garment_types`, proper queries, indexes, and reports. |
| **Add `ON DELETE SET NULL` to `orders.customer_id`** in local SQLite schema | Prevents orphaned orders while preserving order history. |
| **Replace duplicate `useLocalDb()` checks with a data access layer** | Single `db.query()` abstraction that routes to local or cloud. |
| **Add sync failure alert in UI** | Users need visibility into pending queue and errors. |

## 7. Final Summary

### 7.1 Architecture Assessment

The architecture follows a **local-first dual-storage pattern** with these design choices:

| Aspect | Rating | Notes |
|--------|--------|-------|
| **Separation of concerns** | ✅ Good | Separate packages for server, shared types, desktop UI, website |
| **API design** | ✅ Good | RESTful endpoints, consistent auth middleware, audit logging |
| **Data model** | ⚠️ Mixed | JSONB for flexible data is pragmatic but creates query/consistency challenges |
| **Offline support** | ✅ Strong | Local SQLite + sync engine + conflict resolution |
| **Security** | ✅ Good | RLS, token auth, role middleware, owner mode |
| **Error handling** | ⚠️ Mixed | Good HTTP errors, but silent fallbacks in many places |
| **Testing** | ❌ None found | No test files in any package |

### 7.2 What Should Remain Unchanged

- **Sync engine architecture** (push/pull, queue, conflict resolution) is well-designed.
- **Auth middleware stack** (`requireAuth` → `requireRole` → `requireOwnerMode`) is clean and maintainable.
- **Audit logging pattern** is comprehensive and captures most meaningful actions.
- **RLS policies and schema triggers** on Supabase are correct and complete.
- **Type system** (`packages/shared`) is clean and shared between packages.
- **Dual-storage compatibility layer** (Proxy on Supabase query builders for missing columns) is a practical solution for gradual schema migration.

### 7.3 What Should Be Refactored

| Priority | Item | Effort |
|----------|------|--------|
| **High** | Extract data access layer to eliminate duplicate `useLocalDb()` branches in every handler | 2–3 days |
| **High** | Fix local SQLite `orders.customer_id` FK to handle deletion properly | 1 day |
| **High** | Add transaction wrapping for customer+measurement creation in cloud mode | 0.5 day |
| **Medium** | Replace N+1 customer joins in order listing with proper SQL joins (local mode) | 1 day |
| **Medium** | Move `isGarmentTypeUsed()` from JS iteration to a proper DB query | 0.5 day |
| **Medium** | Add server-side validation for prices, quantities, discount values, payment amounts | 1 day |
| **Medium** | Add order status transition FSM validation | 1 day |
| **Low** | Cache settings more selectively (invalidate on change, not per-request) | 0.5 day |
| **Low** | Add measurement history/versioning for audit trail | 2 days |
| **Low** | Instrument `garment_type_id` FK in `order_items` instead of string name | 2 days |

### 7.4 What Should Be Implemented Before Adding New Features

1. **Data access layer abstraction** — Currently every handler has `if (useLocalDb()) { ... } else { ... }` duplication. Extracting this into a `db.query()` abstraction would:
   - Eliminate ~40% of `index.ts` code
   - Reduce bugs from inconsistent implementations
   - Make adding new entities trivial

2. **Order status state machine** — Without FSM validation, simply incrementing a counter (`activeWorkflowStageIds.indexOf(current) + 1`) in the frontend is the only safeguard. A proper DB-level or middleware-level FSM is needed.

3. **Server-side validation consolidation** — Currently validation is split between frontend and backend. Consolidating key validations (prices, payments, measurements, dates) server-side protects against API misuse and sync conflicts.

4. **Sync error visibility** — The sync queue can accumulate failed items with no user notification. At minimum, a badge on the sync indicator showing pending/failed count and a retry-all button.

5. **Order deletion → customer relationship fix** — Either use `ON DELETE SET NULL` in local SQLite or cascade-delete orders when a customer is deleted. Current behavior is inconsistent between cloud and local modes.
